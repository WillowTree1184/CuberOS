# CuberOS Attachable File（COAF）格式规范

## 1. 概述

**COAF**（CuberOS Attachable File）是一种可加载模块文件格式。

本文档使用下列术语：

- **COAF 文件**是符合本文档全部约束的字节序列。
- **映像**（Image）是 COAF 文件中的单个可加载单元。
- **模块**（Module）是映像加载入内存后形成的实体。
- **加载**是将映像变为模块的过程（规定见[第 14 章](#14-加载过程)）。
- **加载器**（Loader）是执行加载的系统组件。
- **宿主**（Host）是执行加载的机器及其指令集架构。
- **制作工具**（Producer）是产生 COAF 文件的工具。

可执行程序与动态链接库在 COAF 中不做格式区分（见 [10](#10-执行模型)）。COAF 具有下列特性：

- 强制位置无关（见 [4.2](#42-imageoffset)）；
- 基于权限的分段（见 [7](#7-段)）；
- 可选数字签名（见 [12](#12-签名)）；
- 一份文件支持多个架构（见 [11](#11-多架构包)）；
- 解析方式完全由版本决定（见 [6.1](#61-version)）。

## 2. 设计哲学

COAF 的每一项规定均可回溯至以下原则。

**归并。** 一个用途只设一个机制；当一个概念能表达为另一概念的特化时，不引入新概念。实例：

- 入口点是特殊的导出符号（见 [10](#10-执行模型)）；
- 可执行程序是特殊的模块（见 [10](#10-执行模型)）；
- 未初始化数据是特殊的段（见 [7.1](#71-coafsegment)）；
- 多架构文件中的每个架构映像是特殊的 COAF 文件——一个内嵌的完整文件（见 [11](#11-多架构包)）。

**最少分派。** 仅当无法避免时才引入按种类分派。除按 Version 分派 MainTable 的解析（见 [6.1](#61-version)，属版本机制）外，COAF 的全部按种类分派点枚举如下：

- 文件起始魔数分派包与映像（见 [5](#5-文件头)、[11](#11-多架构包)）；
- `SignatureBlobOffset` 为零表示无签名（见 [12.2](#122-计算与验证)）；
- 是否导出 `Main` 决定加载后是否调用（见 [10](#10-执行模型)）。

除此之外，任何字段、任何结构均不含条件解释。

**版本即全部。** MainTable 及其所及全部结构的解析完全由 Version 决定（见 [6.1](#61-version)）：结构语义在版本内冻结，取值注册表的扩充不改变解析。COAF 不承担向后兼容义务：支持哪些版本是加载器的实现选择，不是格式的义务。

**拒绝含糊。** 不满足约束的文件无效（见 [13](#13-文件有效性)）；加载器必须拒绝，不得猜测、修补或忽略。

**小体积来自少概念。** COAF 不使用压缩；体积经由概念归并与定长结构控制。

## 3. 基本表示

### 3.1 整数

**U64** 是 8 字节无符号整数。COAF 中所有整数均为 `U64`，以**小端**序存储：最低有效字节位于最低地址。COAF 不存在其他整数宽度与其他字节序。

### 3.2 对齐

每个结构体与每个表的起始 `FileOffset`（见 [4.1](#41-fileoffset)）必须是 8 的倍数。结构体仅由 `U64` 字段与显式字节数组构成，因此不含填充字节；结构体总大小由 `_Static_assert` 固定。

### 3.3 字符串

**字符串**是 UTF-8 编码、以一个字节 `0x00`（NUL）终止的字节序列。字符串仅存在于字符串表（见 [8](#8-字符串表)）中。两个字符串相等，当且仅当其字节序列（不含终止字节）完全相等。

## 4. 地址

COAF 中有且仅有两种地址。每个地址字段的种类由本文档逐字段声明，不得混用。

### 4.1 FileOffset

**FileOffset** 是从文件第 0 字节起算的字节偏移，取值范围为 `[0, 文件大小)`。一切指向文件内容的字段均为 `FileOffset`。内嵌映像（见 [11](#11-多架构包)）内部的 `FileOffset` 相对于内嵌映像自身的第 0 字节。

### 4.2 ImageOffset

**ImageOffset** 是从映像基址起算的字节偏移。**映像基址**（ImageBase）是加载器为映像选定的运行时地址，其取值任意。一切描述内存位置的字段均为 `ImageOffset`。加载后，`ImageOffset` 为 V 的内存位置，其运行时地址等于 `ImageBase + V`。

**位置无关性**（强制）：映像必须构造为可在任意 `ImageBase` 下运行，且必须满足以下所有条件：

- 凡依赖 `ImageBase` 的值，必须经由重定位单元（见 [9.4](#94-relocationtable)）或导入单元（见 [9.3](#93-importsymbol)）表达；
- 除上述单元的内容外，加载后映像的任何字节不得依赖 `ImageBase`。

## 5. 文件头

每个 COAF 文件以一个魔数起始，魔数分派两种文件：映像与包（见 [11](#11-多架构包)）。

```c
#include <stdint.h>

typedef uint64_t U64;

#define CoafMagicImage   0x00474D4946414F43ULL /* 字节序列 "COAFIMG\0" */
#define CoafMagicPackage 0x00474B5046414F43ULL /* 字节序列 "COAFPKG\0" */
```

映像以 **CoafHeader** 起始，其起始的 `FileOffset` 为 0：

```c
typedef struct {
    U64 Magic;           /* 映像魔数 CoafMagicImage */
    U64 Version;         /* 见 6.1 */
    U64 MainTableOffset; /* FileOffset（见 4.1），指向 MainTable（见 6.2） */
} CoafHeader;

_Static_assert(sizeof(CoafHeader) == 24, "CoafHeader");
```

映像文件必须满足以下所有条件：

- `Magic` 必须为 `CoafMagicImage`；
- `MainTableOffset` 必须是 8 的倍数（见 [3.2](#32-对齐)）。

若 `Magic` 为 `CoafMagicPackage`，文件按包处理（见 [11](#11-多架构包)），不适用本章其余规定。`Magic` 为其他取值的文件无效。

## 6. 版本与主表

### 6.1 Version

**Version** 是 `U64` 编号，自 1 起。Version 完全决定 MainTable 的结构以及 MainTable 所及全部结构的解析方式；本文档定义 Version 1。

版本定义一经发布即冻结：不得修改字段，不得追加字段，不得改变字段语义。COAF 的演进经两条互不影响的通道进行：

- 结构演进：任何结构性变更必须发布为新的 Version，且与任何旧 Version 无解释上的耦合；
- 取值演进：`ArchId`（见 [6.3](#63-archid)）与 `Algorithm`（见 [12.1](#121-coafsignatureblob)）的取值注册表可在版本内扩充；由于加载器必须拒绝未知取值，扩充不改变任何既有文件的解析。

加载器必须拒绝其不支持的 Version。加载器支持哪些 Version 由实现自行决定；当生态不再需要某一旧 Version 时，其解析实现可被整体移除。COAF 不为任何 Version 承诺永续支持。

### 6.2 CoafMainTableV1

Version 1 的 MainTable 为 **CoafMainTableV1**：

```c
typedef struct {
    U64 ArchId;                  /* 见 6.3 */
    U64 ImageSize;               /* 映像内存总字节数；约束见 7.1 */
    U64 SegmentTableOffset;      /* FileOffset（见 4.1），见 7.1 */
    U64 SegmentCount;
    U64 ExportSymbolTableOffset; /* 见 9.1 */
    U64 ExportSymbolCount;
    U64 ImportModuleTableOffset; /* 见 9.2 */
    U64 ImportModuleCount;
    U64 ImportSymbolTableOffset; /* 见 9.3 */
    U64 ImportSymbolCount;
    U64 RelocationTableOffset;   /* 见 9.4 */
    U64 RelocationCount;
    U64 StringTableOffset;       /* 见 8 */
    U64 StringTableSize;         /* 字节数 */
    U64 SignatureBlobOffset;     /* FileOffset（见 4.1）；0 表示无签名，见 12 */
} CoafMainTableV1;

_Static_assert(sizeof(CoafMainTableV1) == 120, "CoafMainTableV1");
```

MainTable 必须满足以下所有条件：

- 若某表的 `Count` 为 0，则其对应 `Offset` 必须为 0；
- 若某表的 `Count` 非 0，则其 `Offset` 必须非 0 且为 8 的倍数（见 [3.2](#32-对齐)）；
- 若 `StringTableSize` 为 0，则 `StringTableOffset` 必须为 0。

### 6.3 ArchId

**ArchId** 标识映像的目标指令集架构：

```c
#define CoafArchX86_64      1ULL /* x86-64 */
#define CoafArchAArch64     2ULL /* AArch64 */
#define CoafArchRiscv64     3ULL /* RISC-V 64 */
#define CoafArchLoongArch64 4ULL /* LoongArch64 */
```

其余取值保留。若 `ArchId` 未定义或与宿主不**匹配**，加载器必须拒绝该映像；**匹配**是指映像的 `ArchId` 与宿主的 `ArchId` 相等，宿主的 `ArchId` 由系统决定。新架构通过扩充本注册表获得支持（见 [6.1](#61-version)）。

## 7. 段

### 7.1 CoafSegment

**段**是 COAF 唯一的内容组织单位：代码、只读数据、可写数据均以段表达；COAF 不含「节」概念。

```c
#define CoafPageSize 4096ULL

#define CoafPermRead  1ULL
#define CoafPermWrite 2ULL
#define CoafPermExec  4ULL

typedef struct {
    U64 ImageOffset; /* 见 4.2；段在映像中的起始 */
    U64 FileOffset;  /* 见 4.1；段内容在文件中的起始 */
    U64 FileSize;    /* 段内容在文件中的字节数 */
    U64 MemorySize;  /* 段在内存中的字节数 */
    U64 Permissions; /* 见 7.2 */
} CoafSegment;

_Static_assert(sizeof(CoafSegment) == 40, "CoafSegment");
```

语义：加载后，段的内容按以下规则确定：

- 段占据内存区间 `[ImageBase + ImageOffset, ImageBase + ImageOffset + MemorySize)`；
- 其前 `FileSize` 字节复制自文件的 `[FileOffset, FileOffset + FileSize)`；
- 其余字节为零。

`FileSize` 为 0 的段即未初始化数据——未初始化数据是特殊的段。`CoafPageSize` 是格式常量，与宿主页大小无关。

段表必须满足以下所有条件：

- 段表必须至少含有一项；
- `MemorySize` 不得小于 `FileSize`；
- `ImageOffset` 必须是 `CoafPageSize` 的倍数；
- `MemorySize` 必须大于 0；
- 若 `FileSize` 为 0，则 `FileOffset` 必须为 0；
- `FileOffset + FileSize` 不得超过文件大小；
- `ImageOffset + MemorySize` 不得超过 `ImageSize`（见 [6.2](#62-coafmaintablev1)）；
- `ImageSize` 必须等于各段 `ImageOffset + MemorySize` 的最大值向上对齐到 `CoafPageSize`；
- 任意两段的内存区间不得重叠；
- 段表必须按 `ImageOffset` 严格递增排序。

制作工具应当将 `ImageOffset` 按 16384 字节对齐，以便在页大小超过 `CoafPageSize` 的宿主上保持段间权限的独立性。

### 7.2 段权限

`Permissions` 是 `CoafPermRead`、`CoafPermWrite`、`CoafPermExec` 的位掩码组合，语义分别为可读、可写、可执行。

`Permissions` 必须满足以下所有条件：

- 必须包含 `CoafPermRead`；
- 不得同时包含 `CoafPermWrite` 与 `CoafPermExec`（写执行互斥）；
- 其余位必须为零。

加载器必须以声明值作为段的最终内存保护，且最终化后不得放宽（见 [14](#14-加载过程)）。

## 8. 字符串表

**字符串表**是由 MainTable 的 `StringTableOffset` 与 `StringTableSize`（见 [6.2](#62-coafmaintablev1)）界定的文件区间，内容为字符串（见 [3.3](#33-字符串)）的串联。

名称字段（见 [9](#9-符号与重定位)）是 `FileOffset`（见 [4.1](#41-fileoffset)），直接指向字符串表内某字符串的首字节。

字符串表及其引用必须满足以下所有条件：

- 被引用的名称必须指向字符串表内某字符串的首字节；
- 被引用名称的终止字节必须位于字符串表内；
- 名称必须非空。

同一字符串在表内应当只出现一次；允许后缀共享——字符串「AB」的首字节偏移加 1 即字符串「B」。表内允许存在未被引用的字节。

## 9. 符号与重定位

**导出符号**将名称绑定到本映像内的位置，供其他模块引用；**导入符号**引用其他模块的导出符号。链接在加载时一次性完成（见 [9.5](#95-链接语义)）。

### 9.1 ExportSymbol

```c
typedef struct {
    U64 NameOffset;  /* FileOffset（见 8）；导出名称 */
    U64 ImageOffset; /* 见 4.2；符号所指位置 */
} CoafExportSymbol;

_Static_assert(sizeof(CoafExportSymbol) == 16, "CoafExportSymbol");
```

语义：本映像将名称绑定到运行时地址 `ImageBase + ImageOffset`。

导出符号表必须满足以下所有条件：

- 名称必须非空且不得重复；
- `ImageOffset` 必须落在某段的内存区间内；
- 导出符号表必须按名称的字节序（无符号字节字典序）严格递增排序。

### 9.2 ImportModule

```c
typedef struct {
    U64 NameOffset; /* FileOffset（见 8）；依赖模块名称 */
} CoafImportModule;

_Static_assert(sizeof(CoafImportModule) == 8, "CoafImportModule");
```

语义：声明一个依赖模块的名称。名称到文件的映射由系统约定，不属于 COAF。

导入模块表必须满足以下所有条件：

- 名称必须非空且不得重复；
- 导入模块表必须按名称的字节序严格递增排序。

### 9.3 ImportSymbol

```c
typedef struct {
    U64 ModuleIndex;     /* 导入模块表（见 9.2）的下标 */
    U64 NameOffset;      /* FileOffset（见 8）；导入名称 */
    U64 CellImageOffset; /* 见 4.2；导入单元的位置 */
} CoafImportSymbol;

_Static_assert(sizeof(CoafImportSymbol) == 24, "CoafImportSymbol");
```

**导入单元**是位于本映像内的一个 `U64` 单元。语义：加载器在 `ModuleIndex` 指定的依赖模块的导出符号表中查找名称，将所得运行时地址写入导入单元。代码与数据对模块外符号的一切引用，均经由导入单元间接进行。

导入符号表必须满足以下所有条件：

- `ModuleIndex` 必须小于 `ImportModuleCount`；
- 名称必须非空；
- `ModuleIndex` 与名称的组合不得重复；
- `CellImageOffset` 必须是 8 的倍数；
- `CellImageOffset` 必须指向某可写段（见 [7.2](#72-段权限)）内的 `U64` 单元；
- 任意两导入单元不得共用或交叠；
- 导入符号表必须按（`ModuleIndex`，名称字节序）的字典序严格递增排序。

### 9.4 RelocationTable

**重定位表**是 `U64` 数组，每项是一个 `ImageOffset`（见 [4.2](#42-imageoffset)），指向一个**基址重定位单元**——位于本映像内的一个 `U64` 单元。

语义：加载器对每个基址重定位单元执行：单元值加上 `ImageBase`。加载前，单元内容为 `ImageOffset`。

重定位表必须满足以下所有条件：

- 每项必须是 8 的倍数；
- 每项必须指向某可写段内的 `U64` 单元；
- 各基址重定位单元两两不得共用或交叠；
- 基址重定位单元不得与任何导入单元（见 [9.3](#93-importsymbol)）共用或交叠；
- 重定位表必须严格递增排序。

制作工具应当将导入单元与基址重定位单元集中安置于相邻的段内，以便系统策略在加载完成后对相关页面施加只读保护。

### 9.5 链接语义

解析时机：全部链接在加载时完成；导入符号必须在其使用前完成解析，不存在延迟到运行时的解析。

解析规则：导入符号按（依赖模块，名称）精确匹配该模块的导出符号；解析结果仅取决于该二元组，不受其他模块影响。任何导入符号解析失败，则整个加载失败。

模块同一性：同一加载过程中，名称（字节序列）相同的模块是同一模块；同一模块只加载、重定位、初始化一次。

依赖图：映像的依赖由其导入模块表给出；依赖图必须无环；加载器必须检测并拒绝含环的加载，环检测以模块名称为依赖图的节点。

顺序：依赖先于使用者完成加载、重定位、导入解析与初始化（见 [10](#10-执行模型)、[14](#14-加载过程)）；同一模块的各依赖按其导入模块表中的排列顺序完成初始化。

## 10. 执行模型

**Main** 是保留的导出符号名称。**根模块**是作为进程起点加载的模块。

模块及其全部依赖完成加载、重定位与导入解析后，若模块导出 `Main`，加载器必须调用它；依赖的 `Main` 先于使用者的 `Main` 被调用。根模块的 `Main` 即程序入口。

由此，可执行程序与动态链接库在格式上无区别：可执行程序是导出 `Main` 的模块，入口点是特殊的导出符号。

限制：`Main` 的 `ImageOffset` 必须落在含 `CoafPermExec` 权限的段内（见 [7.2](#72-段权限)）。

`Main` 的调用形式必须满足以下所有约定：

- `Main` 不接受参数；
- `Main` 返回一个 `U64` 状态值；
- 根模块 `Main` 的返回值作为进程退出状态，其余模块 `Main` 的返回值被忽略；
- `Main` 的调用约定遵循 `ArchId`（见 [6.3](#63-archid)）对应架构的系统 ABI。

初始线程与栈的建立、进程参数的传递属系统职责，不属于 COAF。

## 11. 多架构包

**包**是包含若干不同架构映像的 COAF 文件，使一份文件支持多个架构。

```c
typedef struct {
    U64 Magic;      /* 包魔数 CoafMagicPackage（见 5） */
    U64 Version;    /* 包结构版本；规则同 6.1，自 1 起 */
    U64 EntryCount; /* CoafPackageEntry 项数 */
} CoafPackageHeader;

_Static_assert(sizeof(CoafPackageHeader) == 24, "CoafPackageHeader");

typedef struct {
    U64 ArchId;     /* 见 6.3 */
    U64 FileOffset; /* 见 4.1；内嵌映像的起始 */
    U64 Size;       /* 内嵌映像的字节数 */
} CoafPackageEntry;

_Static_assert(sizeof(CoafPackageEntry) == 24, "CoafPackageEntry");
```

结构：`CoafPackageHeader` 起始于 `FileOffset` 0，紧随其后是 `EntryCount` 个 `CoafPackageEntry`。**包项**是 `CoafPackageEntry` 的一项。

**内嵌映像**：包项的 `FileOffset` 处起 `Size` 字节是一个完整的 COAF 映像，即以 `Magic` 为 `CoafMagicImage` 的 `CoafHeader`（见 [5](#5-文件头)）起始；其内部 `FileOffset` 均相对于其自身第 0 字节（见 [4.1](#41-fileoffset)）。提取这些字节即得到与内嵌时完全等价的独立 COAF 文件——内嵌映像是特殊的（内嵌的）COAF 文件。

包必须满足以下所有条件：

- `EntryCount` 必须大于 0；
- 每个包项的 `FileOffset` 必须是 8 的倍数；
- 各内嵌映像的字节区间两两不得重叠；
- 包项的 `ArchId` 不得重复；
- 包项表必须按 `ArchId` 严格递增排序。

制作工具应当使包项的 `ArchId` 与对应内嵌映像 MainTable 的 `ArchId`（见 [6.2](#62-coafmaintablev1)）保持一致。

选择：加载器选取 `ArchId` 与宿主匹配（见 [6.3](#63-archid)）的包项，必须解析所选内嵌映像，并校验其 MainTable 的 `ArchId` 与包项一致；无匹配项则拒绝。加载器将所选字节序列视作一个 COAF 文件，自文件头（见 [5](#5-文件头)）起重新处理。包层不引入签名、符号等其他语义；签名按映像各自进行（见 [12](#12-签名)）。

## 12. 签名

### 12.1 CoafSignatureBlob

```c
#define Ed25519 1ULL /* Ed25519 算法，见下注 */

typedef struct {
    U64     Algorithm;                 /* 签名算法注册表的值，见下注 */
    U64     SignatureSize;             /* Signature 的字节数 */
    uint8_t KeyId[32];                 /* 公钥标识，见下注 */
    uint8_t Signature[];               /* 签名值；C99 灵活数组成员 */
} CoafSignatureBlob;

_Static_assert(sizeof(CoafSignatureBlob) == 48, "CoafSignatureBlob");
```

**Algorithm 与签名算法注册表。** `Algorithm` 是签名算法注册表的值。注册表的每一项必须规定以下所有要素：

- 值与常量名；
- 算法本体；
- 公钥长度；
- `SignatureSize` 的约束。

已定义的项：

- 值 1，常量名 `Ed25519`：
  - 算法本体：Ed25519，即 RFC 8032 定义的纯 EdDSA（Curve25519，内部杂凑为 SHA-512）；
  - 公钥长度：32 字节；
  - `SignatureSize` 约束：必须为 64；
  - 输入约定：算法的输入是消息字节序列本身，其内部杂凑是算法的一部分；产生与验证签名时不得对消息先做预杂凑。

Ed25519 是确定性算法：同一密钥对同一消息的签名值唯一，且验证结果唯一。其余取值保留。新算法通过扩充本注册表获得支持（见 [6.1](#61-version)）；扩充时必须同样给出上列全部要素。

**KeyId。** `KeyId` 是签名公钥的 SHA-256 杂凑（32 字节），与 `Algorithm` 无关，用于在系统信任库中查找公钥。信任库的建立与管理由系统决定，不属于 COAF。

**SignatureSize 与 Signature。** `Signature` 是按 `Algorithm` 对覆盖范围（见 [12.2](#122-计算与验证)）的字节序列计算出的签名值；`SignatureSize` 是 `Signature` 的字节数，必须满足 `Algorithm` 对应注册项的约束。

### 12.2 计算与验证

**所属字节序列。** 每个映像的签名均以其**所属字节序列**为基准：独立映像的所属字节序列是整个文件；内嵌映像（见 [11](#11-多架构包)）的所属字节序列是对应包项给出的、自该项 `FileOffset` 起的 `Size` 个字节。`SignatureBlobOffset`、签名覆盖范围与本节所称「末尾」均相对于该序列的第 0 字节，与包层的其他内容无关。

**位置。** 签名 Blob 必须是所属字节序列的最后若干字节。必须满足以下所有条件：

- 若 `SignatureBlobOffset`（见 [6.2](#62-coafmaintablev1)）非 0，则其必须是 8 的倍数（见 [3.2](#32-对齐)）；
- 若 `SignatureBlobOffset` 非 0，则 `SignatureBlobOffset + 48 + SignatureSize` 必须等于所属字节序列的大小——对独立映像即文件大小，对内嵌映像即包项的 `Size`；
- 若 `SignatureBlobOffset` 为 0，则该映像无签名。

其中 48 是 `Algorithm`、`SignatureSize`、`KeyId` 三个字段的总长度（即不含灵活数组成员的 `sizeof(CoafSignatureBlob)`，见 [12.1](#121-coafsignatureblob)）。

**包中的位置。** 各内嵌映像的签名 Blob 位于该映像自身字节序列的末尾，而不是包文件的末尾；包层无签名，包文件的头部、包项表与间隙不属于任何映像的所属字节序列，不被任何签名覆盖。包项的一致性约束（见 [11](#11-多架构包)）与映像自身的签名共同维持包层完整性：篡改包项至多将选择引向另一个架构相符且自身签名有效的映像。上述等式同时固定了内嵌映像的 `Size`：对带签名映像的任何追加或截断都会使等式不成立，从而被拒绝（见 [13](#13-文件有效性)）。

**计算范围。** 签名覆盖所属字节序列的 `[0, SignatureBlobOffset)`，即除签名 Blob 外的全部字节，包括已写入 `SignatureBlobOffset` 的 MainTable。覆盖范围是该序列的前缀，故签名计算与 Blob 内容之间不存在自引用；`SignatureBlobOffset` 在签名前即已确定（它等于覆盖范围的终点），因此可被安全地包含在覆盖范围内。

**生成流程。** 必须依次执行以下步骤：

1. 完成映像全部内容（含全部表与段）；
2. 取当前序列长度为 `SignatureBlobOffset` 并写入 MainTable；
3. 将 `[0, SignatureBlobOffset)` 的字节序列作为消息，按 `Algorithm` 对应的算法计算签名；
4. 将 `CoafSignatureBlob` 追加到序列末尾。

制作包时，先独立生成并签名各映像，再原样嵌入：嵌入不改变映像的任何字节，故签名在内嵌后仍然有效（见 [11](#11-多架构包)）。

**验证流程。** 必须依次执行以下步骤：

1. 在所属字节序列的 `SignatureBlobOffset` 处读取 `CoafSignatureBlob`；
2. 按 `KeyId` 在系统信任库中取得公钥；信任库中无对应公钥时，验证失败；
3. 将该序列 `[0, SignatureBlobOffset)` 的字节序列作为消息，按 `Algorithm` 对应的算法验证 `Signature`。

加载包时，仅对被选中包项的内嵌映像执行验证（见 [11](#11-多架构包)、[14](#14-加载过程)）。

**策略。** 是否验证、信任哪些密钥，由系统策略决定；COAF 仅规定签名的携带与计算方式。签名是可选支持：无签名的映像不因此无效。

## 13. 文件有效性

本章所称「文件」与「文件大小」，对内嵌映像（见 [11](#11-多架构包)）指其所属字节序列（见 [12.2](#122-计算与验证)）及其 `Size`。

**结构区间**是 `CoafHeader`、MainTable、各表、字符串表、签名 Blob 在文件中占据的字节区间。

文件除须满足各章所列限制外，还须满足以下所有条件方为有效：

1. `CoafHeader` 合法（见 [5](#5-文件头)）；MainTable 的结构与其 Version 相符（见 [6](#6-版本与主表)）。
2. 以下各区间的端点均不超出文件大小：MainTable、各表（`Offset` + `Count` × 元素长度）、字符串表、签名 Blob（见 [12.2](#122-计算与验证)）、各段的文件区间（见 [7.1](#71-coafsegment)）。
3. 对包（见 [11](#11-多架构包)），包项表与各内嵌映像区间的端点均不超出文件大小。
4. 所有结构区间与所有段的文件区间两两不得重叠（允许间隙；制作工具应当不产生间隙）。
5. MainTable 中各 `Offset` 为 8 的倍数（见 [3.2](#32-对齐)）；`Count` 为 0 的表其 `Offset` 为 0，`StringTableSize` 为 0 时 `StringTableOffset` 为 0（见 [6.2](#62-coafmaintablev1)）。
6. 段（见 [7](#7-段)）、字符串引用（见 [8](#8-字符串表)）、符号与重定位（见 [9](#9-符号与重定位)）的全部限制成立。
7. 若 `Magic` 为 `CoafMagicPackage`，包层的全部限制成立（见 [11](#11-多架构包)）。
8. 若 `SignatureBlobOffset` 非 0，签名的全部限制成立（见 [12](#12-签名)）。

加载器必须拒绝无效文件；对有效但其 Version 不受加载器支持的文件，加载器必须拒绝加载。加载器不得忽略或修补文件中的错误。

## 14. 加载过程

加载器必须依次执行以下步骤；任一步骤失败即终止并拒绝该模块：

1. 读取文件起始魔数并分派；若为包，先按[第 11 章](#11-多架构包)的规则完成选择。
2. 依 Version 解析 MainTable（见 [6](#6-版本与主表)）；校验 `ArchId`（见 [6.3](#63-archid)）与全部静态限制（见 [13](#13-文件有效性)）。
3. 若系统策略要求签名验证（见 [12.2](#122-计算与验证)），必须在此完成；验证失败即拒绝。
4. 保留 `ImageSize` 字节的地址空间，其起始即 `ImageBase`（取值任意，见 [4.2](#42-imageoffset)）。
5. 对每个段：以可写但不可执行的权限映射其内存区间，复制文件内容并将其余字节置零（见 [7.1](#71-coafsegment)）。在步骤 9 的最终化之前，任何段不得具有可执行权限。
6. 应用重定位表（见 [9.4](#94-relocationtable)）。
7. 依导入模块表递归加载依赖（拓扑序，检测环，见 [9.5](#95-链接语义)）。
8. 解析全部导入符号并写入导入单元（见 [9.3](#93-importsymbol)）。
9. 将每个段的内存保护最终化为其 `Permissions` 声明值（见 [7.2](#72-段权限)）；最终化后不得放宽。
10. 按[第 10 章](#10-执行模型)的规则处理 `Main`。
